## Part 5: Virtual Circuit Switching — Detailed Working

Your professor's material gives us a more precise model than the earlier introduction.

---

# 1. Why Virtual Circuit Switching?

Your professor summarizes the basic trade-off as:

```text
Circuit Switching
      │
      ├── Reliable / predictable
      │
      └── Inflexible resource allocation


Packet Switching
      │
      ├── Flexible resource allocation
      │
      └── Less predictable delivery


              ↓

Virtual Circuit Switching
              │
      ┌───────┴────────┐
      ↓                ↓
Circuit principles   Packet principles
      │                │
Established path     Buffers
Connection setup     Queuing
      │                │
      └───────┬────────┘
              ↓
       Virtual Circuit
```

The key idea is:

> **VC switching establishes a path like circuit switching, but packets are still buffered and forwarded through a shared packet-switched infrastructure.**

---

# 2. Three Important Properties

Your professor specifically mentions:

### 1. Circuit is established before data transfer

```text
Setup
  ↓
VC established
  ↓
Data transfer
```

### 2. Buffers exist at switches

Packets can wait:

```text
       Router
         │
      ┌──┴──┐
      │ P3  │
      │ P2  │ ← Buffer
      │ P1  │
      └─────┘
         │
         ↓
      Output
```

Therefore, **queuing delay can exist**.

### 3. Resource allocation is flexible

Unlike traditional circuit switching, the underlying network resources can be shared between multiple VCs.

---

# 3. Connection Setup Phase

This is the most important new part of your PPT.

During VC setup, the network creates a:

> **VC Table**

at each switch along the selected path.

Consider:

```text
A ── S1 ── S2 ── S3 ── B
```

Suppose the selected VC path is:

```text
A → S1 → S2 → S3 → B
```

Each switch maintains information about the connection.

---

# 4. What is stored in a VC Table?

Your professor gives four important fields:

| Field              | Meaning                                     |
| ------------------ | ------------------------------------------- |
| Incoming Interface | Interface through which packet arrives      |
| Incoming VCI       | VC identifier carried by incoming packet    |
| Outgoing Interface | Interface through which packet should leave |
| Outgoing VCI       | VCI that will be used on outgoing link      |

Conceptually:

```text id="k9x3vy"
┌──────────────────────────────────────────────┐
│                VC TABLE                     │
├────────────┬────────────┬───────────┬───────┤
│ Incoming   │ Incoming   │ Outgoing  │Outgoing│
│ Interface  │ VCI        │ Interface │ VCI    │
├────────────┼────────────┼───────────┼───────┤
│     1      │    10      │     2     │   25   │
└────────────┴────────────┴───────────┴───────┘
```

This table tells the switch:

> "If a packet comes through interface 1 with VCI 10, send it through interface 2 with VCI 25."

---

# 5. VCI — Virtual Circuit Identifier

A VCI identifies a particular connection **locally at a switch/link**.

This is extremely important.

Suppose:

```text id="n0plju"
A ── S1 ── S2 ── B
```

The VC might use:

```text
A → S1 : VCI 10
S1 → S2: VCI 25
S2 → B : VCI 7
```

Notice:

$$
10\neq25\neq7
$$

That's completely valid.

Why?

Because VCIs are **local in scope**.

---

# 6. What Does "Local Scope" Mean?

Suppose S1 has:

```text
VCI = 10
```

It does **not** mean the entire network must understand "VCI 10".

Instead:

```text id="kfx4za"
At S1:
VCI 10 → connection X

At S2:
VCI 25 → connection X

At S3:
VCI 7 → connection X
```

Each switch can assign its own VCI.

Therefore:

> **VCI values only need to be unique within the relevant local scope, not globally across the entire network.**

This is an important exam concept.

---

# 7. How Is the VCI Chosen?

During setup:

### Step 1

First, a path is selected.

```text id="t10brn"
A → S1 → S2 → S3 → B
```

### Step 2

At each link/switch, a VCI is selected that is not already being used for another connection in that local context.

For example:

```text id="d8cz1u"
S1:

VCI 5  → already used
VCI 6  → already used
VCI 7  → FREE ✓
```

So S1 may assign VCI 7.

Another switch may choose a completely different number.

---

# 8. The Complete VC Setup Example

Let's construct one.

```text id="x3ld5d"
A ── S1 ── S2 ── S3 ── B
```

Suppose the network chooses this path.

During setup, assume the following VCIs are assigned:

```text id="a4w6x2"
A → S1       VCI 12
S1 → S2      VCI 34
S2 → S3      VCI 8
S3 → B       VCI 21
```

The tables could look conceptually like:

### S1

| Incoming Interface | Incoming VCI | Outgoing Interface | Outgoing VCI |
| ------------------ | -----------: | ------------------ | -----------: |
| A-side             |           12 | S2-side            |           34 |

### S2

| Incoming Interface | Incoming VCI | Outgoing Interface | Outgoing VCI |
| ------------------ | -----------: | ------------------ | -----------: |
| S1-side            |           34 | S3-side            |            8 |

### S3

| Incoming Interface | Incoming VCI | Outgoing Interface | Outgoing VCI |
| ------------------ | -----------: | ------------------ | -----------: |
| S2-side            |            8 | B-side             |           21 |

---

# 9. Data Transfer Phase

Now the setup is complete.

A sends a packet.

Suppose:

```text id="h2dyc8"
Packet:

VCI = 12
Data = ...
```

The packet arrives at S1.

S1 looks at:

```text
Incoming interface = A-side
Incoming VCI = 12
```

It searches the VC table:

```text id="9m2d52"
(A-side, 12)
       ↓
     S1 VC table
       ↓
(S2-side, 34)
```

So S1 changes the packet's VCI:

```text
VCI 12 → VCI 34
```

and sends it through the S2 interface.

---

# 10. At S2

S2 receives:

```text
Incoming interface = S1-side
VCI = 34
```

It looks up:

```text id="p1g3sn"
(S1-side, 34)
        ↓
      S2 table
        ↓
(S3-side, 8)
```

So:

```text
VCI 34 → VCI 8
```

and forwards the packet.

---

# 11. At S3

S3 receives:

```text
Incoming interface = S2-side
VCI = 8
```

Lookup:

```text id="x2k7vy"
(S2-side, 8)
        ↓
      S3 table
        ↓
(B-side, 21)
```

Therefore:

```text
VCI 8 → VCI 21
```

and the packet reaches B.

---

# 12. The Whole Process

This is worth memorizing:

```text id="5x8pml"
              VC SETUP
                  │
                  ↓
        Select path A → B
                  │
                  ↓
        Assign VCIs locally
                  │
                  ↓
       Build VC tables
                  │
                  ↓
          DATA TRANSFER
                  │
                  ↓
       Packet arrives at switch
                  │
                  ↓
         Read incoming VCI
                  │
                  ↓
          Lookup VC table
                  │
                  ↓
     Find outgoing interface + VCI
                  │
                  ↓
       Replace/update VCI
                  │
                  ↓
       Forward packet
                  │
                  ↓
          Repeat at every switch
```

This is probably the **most important technical diagram from this PPT**.

# 13. Why Is VC Lookup Faster Than Packet Switching?

Your professor states:

> **Lookup time is better than packet switching.**

Why?

In ordinary IP forwarding, a router may need to perform a **longest-prefix match**.

For example:

```text
Destination IP:
192.168.10.25
```

The router needs to determine which prefix matches.

Potential entries:

```text
192.168.0.0/16
192.168.10.0/24
192.168.10.16/28
...
```

The router needs the **longest matching prefix**.

---

## VC Switching

VC forwarding can use an **exact match**:

```text
Incoming interface = 2
VCI = 17

        ↓

Exact table entry
        ↓

Outgoing interface = 4
Outgoing VCI = 32
```

Therefore:

$$
\boxed{\text{VC → Exact matching}}
$$

rather than:

$$
\boxed{\text{IP → Longest Prefix Matching}}
$$

This can simplify forwarding.

---

# 14. Why Are VC Packet Headers "Lightweight"?

A datagram packet generally carries a full destination address.

For example, conceptually:

```text
Destination IP = 192.168.10.25
```

A VC packet can carry something much smaller:

```text
VCI = 17
```

Therefore, the packet header can be relatively small.

Your professor calls this:

> **Light packet header and lightweight packets**

---

# 15. Fixed Routes

Your professor states:

> **Routes are fixed during the circuit setup process.**

Suppose:

```text id="lj2s0a"
A → S1 → S2 → S4 → B
```

Once the VC is established, packets belonging to that VC use that logical path.

If the route becomes unavailable:

```text id="d5x1sp"
A → S1 → S2 ✕ S4 → B
```

the VC may need to be re-established or otherwise handled by the network.

This leads directly to another point from your PPT:

> **VC switching has to recover from connection failures.**

---

# 16. The RTT Setup Cost

This is an important point that we didn't emphasize enough earlier.

Your professor says:

> **Delay of 1 RTT before sending actual data**

### RTT = Round Trip Time

Suppose:

```text id="2q2d6h"
A ─────────────→ B
     Setup

A ←───────────── B
     Reply
```

A sends the connection setup request.

The network/destination responds.

Only then can A begin normal data transmission.

So approximately:

$$
\boxed{T_{setup}\approx1RTT}
$$

under the simplified assumption in the PPT.

---

# 17. Why Is This a Disadvantage?

For a very small amount of data:

```text
Setup:       ██████████
Actual data: ██
```

The setup overhead can be significant.

For a long communication:

```text
Setup:       █
Data:        ███████████████████████████
```

the setup cost becomes relatively small compared with the total communication.

Therefore VC switching is more attractive when the connection is sufficiently long-lived to amortize the setup cost.

---

# 18. VC Switching and Queuing

Unlike traditional circuit switching, VC switches can have buffers.

```text id="b2kl1q"
             Switch
                │
       ┌────────┴────────┐
       │     BUFFER      │
       ├─────────────────┤
       │ P3              │
       │ P2              │
       │ P1              │
       └─────────────────┘
                │
                ↓
             Output
```

Therefore:

$$
\boxed{\text{VC can experience queuing delay}}
$$

This is one reason your professor says:

> **QoS is better than packet switching but less than circuit switching.**

That's a simplified course-level characterization. The exact QoS depends on the particular VC technology and whether resources/QoS mechanisms are configured.

# 23. What is MPLS?

MPLS stands for:

$$
\boxed{\text{Multiprotocol Label Switching}}
$$

The key idea:

> Instead of forwarding packets solely by repeatedly examining the full destination IP address, MPLS routers can forward packets using relatively short **labels**.

Conceptually:

```text id="s8a0hq"
IP packet
   ↓
MPLS label
   ↓
Label-based forwarding
```

This resembles VC switching.

---

# 24. Why Does MPLS Look Like Virtual Circuit Switching?

Your professor explicitly says:

> MPLS combines properties of virtual circuits with flexibility and robustness of datagrams.

The similarities include:

### 1. Labels have local scope

Just like VCIs.

### 2. Short labels

Instead of repeatedly working with a full destination address.

### 3. Label-based forwarding

Routers inspect the label to decide what to do.

So:

```text id="wz4f5j"
Virtual Circuit:

VCI → lookup → outgoing interface + VCI


MPLS:

Label → lookup → outgoing interface + label
```

---

# 25. MPLS Router Terminology

Two terms from your PPT are important.

### LER

$$
\boxed{\text{Label Edge Router}}
$$

The router at the edge of an MPLS network.

Example:

```text id="b7dr46"
IP Network
    │
    ↓
   LER
    │
    ↓
MPLS Network
```

---

### LSR

$$
\boxed{\text{Label Switch Router}}
$$

Routers inside the MPLS network that forward packets based on labels.

Your professor's example:

```text id="zjaf4m"
R1 → R2 → R3 → R4
```

may have:

```text
R1 = LER
R2 = LSR
R3 = LSR
R4 = LSR
```

depending on the topology and role.

---

# 26. Label Switching

Suppose:

```text id="xq07fd"
R1 → R2 → R3 → R7
```

An incoming packet has:

```text
Label = 20
```

R2 looks at:

```text
Incoming label = 20
```

and performs a lookup:

```text id="3y8o9c"
20 → outgoing interface + label 35
```

Then:

```text
Label 20
   ↓
R2
   ↓
Label 35
```

This process is called:

> **Label swapping**

---

# 27. Label Swapping

This is one of the most important MPLS concepts.

```text id="g6s8b1"
        R1             R2             R3
        │              │              │
Packet  │              │              │
Label 10 ─────────────→│              │
                       │              │
                   Label 10           │
                       │              │
                       └─→ Label 25 ─→│
                                      │
                                      ↓
```

The label changes at each hop.

So:

$$
\boxed{\text{MPLS uses label swapping}}
$$

This is analogous to VCI translation in VC switching.

# 28. Explicit Routing

Now we reach another important MPLS feature.

Normal IP routing may choose a path based on routing algorithms.

But suppose the network administrator wants:

```text id="rvz7bw"
R1 → R3 → R6 → R7
```

for traffic from R1 to R7.

And:

```text id="8ahb6b"
R2 → R3 → R4 → R5 → R7
```

for traffic from R2 to R7.

These are **explicit routes**.

MPLS can support this kind of traffic engineering.

---

# 29. Why Is Explicit Routing Useful?

Suppose normal routing produces:

```text id="a3h8lz"
R1 → R2 → R4 → R7
```

But perhaps this route has:

* congestion
* insufficient capacity
* undesirable latency
* policy constraints

An explicitly engineered path might instead be:

```text id="x3kq4a"
R1 → R3 → R6 → R7
```

MPLS can help implement such traffic-engineered paths.

---

# 30. Why Use MPLS?

Your professor gives three major reasons.

### 1. Support IP capabilities on devices

MPLS can provide label-based forwarding within the network.

### 2. Explicit routing

Traffic can be directed along precomputed/engineered paths that differ from ordinary IP routing choices.

### 3. VPN services

MPLS is widely used to support certain provider-based VPN architectures.

---

# 31. MPLS and VPNs

Your PPT says:

> VPNs provide a dedicated path for certain network packets using the concept of tunnels.

The key idea is **tunneling**.

Imagine:

```text id="1uj4cc"
Office A
   │
   ↓
======== Provider Network ========
   │
   ↓
Office B
```

Instead of treating the entire provider network as something the customer needs to understand, traffic can be carried through a logical tunnel.

Conceptually:

```text id="5wx8t7"
A ═════════════════════════ B
       Logical tunnel
```

The underlying physical infrastructure remains shared.

---

# 32. Important Distinction: VPN vs Physical Dedicated Line

A VPN does **not necessarily mean a physically dedicated cable**.

Instead:

> It provides logical isolation/connectivity over shared infrastructure.

This is conceptually similar to the "virtual" idea in virtual circuits.

## 🔥 One particularly important exam question

If your professor asks:

> **"Explain how a packet is forwarded in a Virtual Circuit network."**

Your answer should be:

```text
1. A VC is established during setup.
          ↓
2. A path is selected from source to destination.
          ↓
3. Each switch creates a VC-table entry.
          ↓
4. The entry maps:
   (Incoming Interface, Incoming VCI)
          ↓
   (Outgoing Interface, Outgoing VCI)
          ↓
5. During data transfer, the switch reads the incoming VCI.
          ↓
6. It performs an exact lookup in the VC table.
          ↓
7. It replaces the VCI with the outgoing VCI.
          ↓
8. It forwards the packet through the outgoing interface.
          ↓
9. The process repeats at every switch.
```

That is a **very strong 5–10 mark answer** because it demonstrates the actual mechanism rather than simply defining VC switching.
