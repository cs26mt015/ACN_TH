## Topic 5: Switching Fabrics

This is a **high-weight topic** in your PPT because it combines architecture, packet movement, scheduling, performance, and several important numerical/conceptual questions.

---

# 1. What is a Switching Fabric?

A **switching fabric** is the internal mechanism of a router that provides a path between an **ingress line card** and an **egress line card**.

Think of it as the router's internal transportation system.

```text
                    ROUTER
        ┌─────────────────────────────┐
        │                             │
Packet →│ Ingress Line Card           │
        │        │                    │
        │        ↓                    │
        │  ┌───────────────┐          │
        │  │   Switching   │          │
        │  │    Fabric     │          │
        │  └───────┬───────┘          │
        │          ↓                  │
        │  Egress Line Card           │→ Packet
        │                             │
        └─────────────────────────────┘
```

It is also called:

> **Switching Backplane**

---

# 2. Where Does Switching Fabric Fit?

Recall the packet path:

```text
Incoming Packet
      ↓
Ingress Line Card
      ↓
Forwarding Lookup
      ↓
Switching Fabric
      ↓
Egress Line Card
      ↓
Output Queue
      ↓
Outgoing Link
```

The ingress line card determines **where the packet needs to go**.

The switching fabric provides the **internal path to that destination**.

---

# 3. Main Functions of Switching Fabric

A good switching fabric should:

### 1. Transfer packets between line cards

```text
Input → Fabric → Output
```

### 2. Support multiple transfers simultaneously

Ideally:

```text
Input 1 → Output 1
Input 2 → Output 2
Input 3 → Output 3
```

at the same time.

### 3. Provide fair bandwidth allocation

No input/output should be unfairly starved.

### 4. Avoid unnecessary packet reordering

Packets belonging to the same flow should ideally maintain their order.

### 5. Support priority

Higher-priority traffic should receive appropriate service.

# 4. Three Primary Performance Metrics

Your PPT identifies three major metrics:

$$
\boxed{Throughput}
$$

$$
\boxed{Latency}
$$

$$
\boxed{Path\ Diversity}
$$

Let's understand them.

---

## Throughput

How much traffic can the switching fabric transfer per unit time?

Example:

$$
100\,Gbps
$$

means the fabric can transfer approximately 100 billion bits per second under the relevant conditions.

---

## Latency

How long does it take to move a packet through the fabric?

Lower latency is generally desirable for delay-sensitive traffic.

---

## Path Diversity

The ability to provide multiple internal paths between inputs and outputs.

More path diversity can help:

* parallel transfers
* load distribution
* fault tolerance

# 5. Switching Fabric Architecture

Your PPT describes four important components.

```text
                 SWITCHING FABRIC
        ┌─────────────────────────────┐
        │                             │
Input → │ Fabric Input Interface     │
        │        ↓                    │
        │ Fabric Input Buffer        │
        │        ↓                    │
        │      Scheduler              │
        │        ↓                    │
        │ Fabric Output Interface    │
        │        ↓                    │
        │ Fabric Output Buffer       │
        │                             │
        └─────────────────────────────┘
```

---

# 6. Fabric Input Interface

The **fabric input interface** connects the ingress processing portion of the line card to the switching fabric.

It also coordinates with the scheduler regarding packet availability.

In simple terms:

> It tells the fabric that packets are waiting to be transferred.

---

# 7. Fabric Input Buffer

Packets may arrive faster than the switching fabric can immediately transfer them.

Therefore, temporary storage is required.

That is the:

> **Fabric input buffer**

```text
Packets arrive
      ↓
Input Buffer
      ↓
Waiting for fabric
```

The buffer helps prevent immediate packet loss when the fabric cannot serve a packet immediately.

---

# 8. Fabric Output Interface

After the fabric transfers the packet, the output interface receives it and passes it toward the egress processing module.

```text
Switching Fabric
       ↓
Output Interface
       ↓
Egress Line Card
```

---

# 9. Fabric Output Buffer

The packet may arrive at the output faster than the outgoing interface can transmit it.

Therefore, it may need to wait.

The:

> **Fabric output buffer**

stores such packets temporarily.

```text
Fabric
  ↓
Output Buffer
  ↓
Transmission
```

---

# 10. Packet Flow Through a Router

Let's combine everything.

### Ingress

The incoming packet is processed:

* IP header located
* Header validated
* Relevant information extracted
* Forwarding lookup performed
* Packet classification may occur
* Packet placed in appropriate buffer

Then:

```text
Ingress
   ↓
Forwarding Engine
   ↓
Input Buffer
```

---

# 11. Scheduling

Now comes a very important component:

> **Scheduler**

The scheduler decides:

> Which input should communicate with which output during a given time slot?

For example:

```text
Inputs              Outputs

I1 ───────────────→ O2
I2 ───────────────→ O4
I3 ───────────────→ O1
I4 ───────────────→ O3
```

The scheduler creates these connections.

---

# 12. What is a Timeslot?

A **timeslot** is a fixed interval during which a particular set of input-output transfers occurs.

For example:

```text
Timeslot 1:
I1 → O1
I2 → O3

Timeslot 2:
I1 → O2
I3 → O4

Timeslot 3:
I2 → O1
I4 → O3
```

The scheduler determines the configuration for each timeslot.

---

# 13. Shared Backplane

Now we come to the first major type of switching fabric.

## Shared Backplane

A shared backplane uses a **shared medium** to transfer packets between line cards.

Example:

```text
        Input 1
           │
        Input 2
           │
        Input 3
           │
           ↓
     ┌───────────┐
     │Shared Bus │
     └───────────┘
       │   │   │
       ↓   ↓   ↓
      O1  O2  O3
```

All line cards share the same internal resource.

---

# 14. Limitation of Shared Backplane

Because the medium is shared:

> Multiple transfers cannot freely occur simultaneously on the same shared resource.

Therefore, aggregate throughput is limited.

Shared backplanes are typically associated with lower-bandwidth router designs.

Example:

> **Shared bus**

---

# 15. Switched Backplane

A **switched backplane** allows multiple transfers to occur simultaneously.

```text
I1 ─────→ O1
I2 ─────→ O2
I3 ─────→ O3
```

This increases aggregate throughput.

The key component is:

> **Scheduler**

The scheduler determines which input-output pairs are connected during each timeslot.

---

# 16. Shared vs Switched Backplane

| Shared Backplane               | Switched Backplane          |
| ------------------------------ | --------------------------- |
| Shared medium                  | Multiple internal paths     |
| Limited simultaneous transfers | Supports parallel transfers |
| Lower aggregate throughput     | Higher aggregate throughput |
| Simpler                        | More complex                |
| Example: shared bus            | Example: crossbar           |

---

# 17. Crossbar Switch

This is one of the most important concepts.

An:

$$
\boxed{N\times N}
$$

crossbar has:

* N input buses
* N output buses
* \(N^2\) crosspoints

For example:

### 4 × 4 crossbar

$$
4^2=16
$$

crosspoints.

```text
             Outputs
          O1  O2  O3  O4
          │   │   │   │
I1 ───────●───●───●───●
I2 ───────●───●───●───●
I3 ───────●───●───●───●
I4 ───────●───●───●───●
```

Each dot is a crosspoint.

---

# 18. What is a Crosspoint?

A crosspoint represents a possible connection between:

$$
Input_i
$$

and:

$$
Output_j
$$

For example:

$$
(i,j)=(2,3)
$$

means:

> Input 2 can be connected to Output 3.

The crosspoint can be:

* ON
* OFF

---

# 19. Why is Crossbar Fast?

Suppose:

```text
I1 → O1
I2 → O2
I3 → O3
I4 → O4
```

These can occur simultaneously.

Therefore:

$$
4\text{ packets}
$$

can potentially be transferred during one timeslot.

This is much better than a single shared bus where transfers compete for a shared medium.

---

# 20. But Crossbar Has a Problem

Suppose:

```text
I1 → O1
I2 → O1
I3 → O3
I4 → O4
```

Both I1 and I2 want the same output:

```text
        → O1
I1 ─────┤
I2 ─────┘
```

But O1 can normally receive only one packet per timeslot.

Therefore:

```text
I1 → O1  ✓
I2 → O1  ✗
```

One packet must wait.

This creates contention.

---

# 21. Another Problem — Idle Inputs

Suppose only:

```text
I1 → O1
```

has traffic.

Then:

```text
I2 → nothing
I3 → nothing
I4 → nothing
```

Their available transmission opportunities remain unused.

Therefore, the crossbar may have unused capacity.

This contributes to lower utilization.

---

# 22. Why Do We Need a Scheduler?

The scheduler decides which connections should be active.

For example:

```text
Requests:

I1 → O1
I2 → O1
I3 → O3
I4 → O4
```

Scheduler might choose:

```text
I1 → O1
I3 → O3
I4 → O4
```

and reject/postpone:

```text
I2 → O1
```

for this timeslot.

---

# 23. Important Constraint

In a basic crossbar schedule:

> An input cannot simultaneously send to multiple outputs during the same timeslot.

And:

> An output cannot simultaneously receive from multiple inputs during the same timeslot.

Therefore, a valid schedule is essentially a set of **non-conflicting input-output matches**.

---

# 24. Crossbar Utilization

Suppose:

$$
N=4
$$

Then there are 4 possible transfers per timeslot.

Suppose over 3 timeslots:

$$
Maximum\ opportunities=3\times4=12
$$

but only 8 packets are actually transferred.

Utilization:

$$
\frac{8}{12}\times100
$$

$$
\boxed{66.67\%}
$$

This type of numerical can easily appear in an exam.

---

# 25. Why Can Utilization Be Low?

Your PPT identifies:

1. **Head-of-Line Blocking**
2. **Input Blocking**
3. **Output Blocking**
4. Idle inputs/outputs
5. Contention for the same output

The most important one is:

> **HOL — Head-of-Line Blocking**

---

# 26. Head-of-Line Blocking

Suppose every input has a FIFO queue.

```text
Input 1:
[P1 → O1] [P2 → O2] [P3 → O3]

Input 2:
[P4 → O2] [P5 → O3]

Input 3:
[P6 → O3]
```

The first packet in each queue is the **head-of-line packet**.

Suppose:

```text
P1 → O1
P4 → O2
P6 → O3
```

Everything works.

But consider:

```text
Input 1:
[P1 → O1] [P2 → O2]

Input 2:
[P3 → O1] [P4 → O3]
```

Suppose P1 wins access to O1.

Then P3 cannot use O1 in the same timeslot.

But more importantly:

```text
Input 2:
[P3 → O1] [P4 → O3]
```

P4 wants O3, which is free.

However, because P3 is stuck at the **head** of the FIFO queue, P4 cannot move forward.

Therefore:

> A packet at the head of a queue can block packets behind it even when their desired outputs are free.

This is **Head-of-Line Blocking**.

---

# 27. Why is HOL Blocking Bad?

Because it reduces switch utilization.

Some output ports may remain idle even though packets are waiting at input queues that could otherwise use those outputs.

```text
Output O3 = FREE

But:

Input queue:
[P1 → O1] [P2 → O3]

P1 is blocked
      ↓
P2 cannot move
      ↓
O3 remains idle
```

This wastes available switching capacity.

---

# 28. Three Important Queueing Strategies

To address HOL blocking, we study:

### 1. Input Queueing

Queues at input ports.

### 2. Output Queueing

Queues at output ports.

### 3. Virtual Output Queueing — VOQ

Multiple queues at each input, one for each output.

These are extremely important for exams.

---

# 29. Input Queueing

Each input has one FIFO queue.

```text
Input 1 → [P1][P2][P3]
Input 2 → [P4][P5][P6]
Input 3 → [P7][P8][P9]
```

Simple to implement.

But:

> **It suffers from HOL blocking.**

---

# 30. Output Queueing

Instead of queues at inputs, packets are immediately transferred toward their destination output queues.

```text
             ┌→ O1 Queue
Inputs ──────┼→ O2 Queue
             └→ O3 Queue
```

Now packets don't get stuck behind packets destined for another output at the input.

Therefore:

> **HOL blocking is eliminated.**

---

# 31. Problem with Output Queueing

Suppose there are:

$$
N
$$

input ports.

All N inputs simultaneously send packets to the same output.

Then:

```text
I1 ─┐
I2 ─┤
I3 ─┤──→ O1
... │
IN ─┘
```

The output queue must receive N packets in the time normally needed for one packet arrival.

Therefore:

$$
\boxed{\text{Switch fabric must operate approximately }N\text{ times faster}}
$$

than the input line rate in the worst case.

---

# 32. Example

Suppose:

$$
N=4
$$

and every input link operates at:

$$
1\,Gbps
$$

Then the output side may need to absorb:

$$
4\times1=4\,Gbps
$$

in the worst case.

Thus the switching fabric/output queue would need very high speed.

---

# 33. Output Queueing — Pros and Cons

### Advantages

* Eliminates HOL blocking.
* Theoretically allows 100% throughput under appropriate conditions.

### Disadvantages

* Fabric may need to operate N times faster.
* Output queues need extremely high-speed operation.
* Expensive/difficult to implement.

---

# 34. Virtual Output Queueing — VOQ

VOQ is a very important solution.

Instead of:

```text
Input 1:
[P1][P2][P3]
```

we create separate queues based on destination output.

For a 4-output switch:

```text
Input 1:

VOQ1 → packets for O1
VOQ2 → packets for O2
VOQ3 → packets for O3
VOQ4 → packets for O4
```

Diagram:

```text
                Input 1
             ┌────────────┐
             │ VOQ → O1   │
             │ VOQ → O2   │
             │ VOQ → O3   │
             │ VOQ → O4   │
             └────────────┘
```

---

# 35. Why Does VOQ Solve HOL Blocking?

Consider:

```text
Input 1:

VOQ1: [P1 → O1]
VOQ2: [P2 → O2]
```

Suppose O1 is currently busy.

With a single FIFO:

```text
[P1 → O1] [P2 → O2]
```

P2 could be blocked by P1.

With VOQ:

```text
VOQ1 → O1  BLOCKED
VOQ2 → O2  FREE
```

The scheduler can select P2.

Therefore:

> Packets destined for different outputs don't block one another merely because they arrived behind another packet.

---

# 36. Number of VOQs

For an:

$$
N\times N
$$

switch:

Each input needs:

$$
N
$$

queues.

There are:

$$
N
$$

inputs.

Therefore:

$$
\boxed{N^2}
$$

total VOQs.

### Example

For a:

$$
8\times8
$$

switch:

$$
8^2=64
$$

VOQs.

---

# 37. VOQ Advantages

### Advantage 1

Eliminates HOL blocking in the basic input-queueing architecture.

### Advantage 2

Can theoretically achieve:

$$
\boxed{100\%}
$$

throughput under suitable assumptions with an appropriate scheduler.

### Advantage 3

Doesn't require the switching fabric to run N times faster like pure output queueing.

---

# 38. VOQ Disadvantage

The major disadvantage is:

> **Scheduler complexity.**

The scheduler must examine many queues and determine which input-output pairs can be simultaneously matched.

For an:

$$
N\times N
$$

switch, there are:

$$
N^2
$$

VOQs.

As N increases, scheduling becomes increasingly difficult.

---

# 39. Enter PIM

This leads us to:

> **Parallel Iterative Matching — PIM**

PIM is a scheduling algorithm designed to quickly find a large set of valid input-output matches.

The basic goal is:

> Maximize the number of packets transferred during each timeslot while respecting input/output conflicts.

---

# 40. Basic Idea of PIM

Suppose:

```text
Inputs:
I1 I2 I3 I4

Outputs:
O1 O2 O3 O4
```

There are many requests:

```text
I1 → O1
I1 → O2
I2 → O1
I3 → O3
I4 → O4
```

The scheduler needs to select a conflict-free set.

For example:

```text
I1 → O2
I2 → O1
I3 → O3
I4 → O4
```

All four transfers can happen simultaneously.

PIM uses multiple iterations to converge toward a large/maximal matching quickly.

---

# 41. Why "Parallel"?

Because matching decisions for multiple inputs/outputs can be considered in parallel rather than processing every request sequentially.

This makes PIM suitable for high-speed switches.

---

# 42. Why "Iterative"?

One iteration may not produce a sufficiently good matching.

So the scheduler repeats the matching process:

```text
Requests
   ↓
Iteration 1
   ↓
Partial Matching
   ↓
Iteration 2
   ↓
Improved Matching
   ↓
...
   ↓
Final Matching
```

The objective is to obtain a large/maximal matching within the available scheduling time.

---

# 43. The Big Picture

You should understand the evolution:

```text
Input Queueing
      ↓
HOL Blocking
      ↓
Problem
      ↓
Output Queueing
      ↓
HOL eliminated
      ↓
But requires N× speed
      ↓
Problem
      ↓
Virtual Output Queueing
      ↓
HOL eliminated
      ↓
But scheduler becomes complex
      ↓
PIM
      ↓
Fast scheduling / large matching
```

This chain is **very important for theory questions**.

# 45. Exam-Level Conceptual Question

### Why doesn't output queueing suffer from HOL blocking?

Because packets are not forced to wait behind packets destined for another output at the same input FIFO queue.

They are directly placed into the queue corresponding to their destination output.

# 46. Another Exam Trap

### Is VOQ the same as output queueing?

**No.**

### Output Queueing

Queues are physically maintained at:

```text
OUTPUT
```

### VOQ

Multiple destination-specific queues are maintained at:

```text
INPUT
```

Remember:

$$
\boxed{VOQ =\ Virtual\ Output\ Queues\ at\ Inputs}
$$
